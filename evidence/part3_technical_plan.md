**Đề xuất tối thiểu:** DB-backed worker loop/polling vì nó tận dụng persisted intent và lease fields, hoạt động độc lập với Rabbit runtime chưa có. Đây là lựa chọn thiết kế mới, không phải mô tả hiện trạng. Thêm scheduler/worker sau khi review; không đưa HTTP call vào transaction tạo Order. Cấu hình lịch/batch/concurrency/lease lấy từ yêu cầu/runtime được duyệt, không tự đặt giá trị tại plan này.

### Claim, lease, fencing và process flow

1. Sau commit của POST, worker query các due `NOT_STARTED` steps. Không coi `findRetryable` là claim; hiện nó đọc cả `IN_PROGRESS` và không lọc lease/token (`SagaRepository.java:65-69`).
2. Bổ sung atomic claim transaction: chọn một row due theo locking/skip-locked hoặc conditional UPDATE, đổi status/token/timestamps/lease một lượt, và trả row+token. Mỗi worker chỉ dispatch row được claim thành công. Cần chốt query semantics khi status `IN_PROGRESS`, lease hết hạn, và query UNKNOWN; finder `findExpiredLeases` hiện chỉ tìm, không takeover (`SagaRepository.java:77-80`).
3. `claim_token` hiện là UUID, nên có thể làm owner token để fence **các ghi DB** bằng equality với token hiện hành; không phải fencing sequence có thứ tự và Inventory không kiểm tra token này. Mọi persist result/renew/release claim phải có điều kiện theo step ID + token hiện hành (và expected status). `updateStep` hiện không nhận token nên cần bổ sung guard; nếu worker A hết lease, B takeover, phản hồi A đến trễ thì A không được ghi đè B. Lease/heartbeat và HTTP timeout cần phối hợp để giảm request overlap; dù overlap xảy ra, Inventory stable idempotency key là lớp chặn business effect thứ hai.
4. Ghi SEND attempt và claim một cách nhất quán; `insertAttempt` hiện tự tăng counter nhưng không kiểm tra claim owner (`SagaRepository.java:83-105`). Chọn thứ tự sao cho crash sau claim nhưng trước HTTP vẫn recoverable qua lease; không đánh dấu definitive fail.
5. Commit claim transaction rồi gọi HTTP **ngoài transaction**. Sau response, mở transaction ngắn và ghi Order reservation outcome + Saga step outcome + Saga branch/Order status đồng bộ. Cần đảm bảo handler result atomically ghi kết quả step và status để tránh Order/step lệch nhau. Việc gọi nhiều method `@Transactional` phải qua Spring proxy/transaction chung; không dựa vào self-invocation để tạo transaction.
6. Verified `RESERVED`: ghi Order reservation `RESERVED,true`; Saga RESERVE step `SUCCEEDED/NONE`, giữ Order `PENDING`; không thêm CAPTURE trong slice. Verified `REJECTED`: ghi Reservation `REJECTED,true`; Saga RESERVE step `FAILED/BUSINESS`; gọi conditional start compensation; Order/Saga status `COMPENSATING`. UC-02-A của requirements mô tả Inventory rejection đưa Order `PENDING→COMPENSATING`, không cần release nếu không giữ hàng, rồi có thể kết thúc FAILED; tuy nhiên phần slice này chỉ yêu cầu đến `COMPENSATING` (`docs/requirements/08-detailed-use-cases.md:214-223`). `updateSagaBranch` không thay `current_operation`, nên ý nghĩa giá trị hiện là RESERVE sau branch switch cần được xác nhận hoặc điều chỉnh khi thiết kế transition; không tự đưa ra trạng thái operation mới.
7. Worker chết trước HTTP: lease hết hạn và row có thể claim lại. Worker chết sau Inventory commit nhưng trước local result: retry/query phải dùng cùng key/payload; Inventory replay/query trả effect gốc. Không mở transaction DB qua network.

### Retry và UNKNOWN

- Tạm phân loại theo evidence: 200 + body `RESERVED/REJECTED` là definitive result nếu parse/validate theo contract; 4xx validation/key conflict là lỗi protocol/config, không đổi thành business rejection; 5xx/transport timeout không đủ chứng cứ effect chưa xảy ra. Lỗi runtime/response malformed cũng không được tự hiểu là `REJECTED`.
- Khi request có thể đã tới Inventory nhưng response bị timeout/lost, persist Saga step `UNKNOWN/UNKNOWN` và Reservation `UNKNOWN`/operation `RESERVE`, chưa verified. Khi có bằng chứng chắc chắn request chưa được gửi/không thể tới service, có thể xử lý như transient `IN_PROGRESS/TRANSIENT` và retry theo policy. Schema cho phép UNKNOWN; transition API hỗ trợ recordReservation UNKNOWN (`OrderStateMachine.java:29-40`), failure_class check yêu cầu `UNKNOWN` status UNKNOWN (`V004:1-9`). Sau UNKNOWN, query Inventory bằng `orderId` hoặc idempotency key; không mark FAILED/COMPENSATING từ timeout.
- Repository `findReconciliationDue` và Inventory GET by orderId/idempotencyKey có thể hỗ trợ reconciliation (`SagaRepository.java:71-75`; `InventoryController.java:49-69`; `14-inventory-api-contract.md:60-67`). Nhưng no worker implements them. A 404 is not definitive that in-flight Reserve cannot complete; query again or replay same Reserve safely according to approved retry policy.
- For definitive transient failure known not committed, store failure_class `TRANSIENT` while step remains `IN_PROGRESS` and `next_attempt_at` populated (V004 constraint); retry same command/key/request. Requirements D-03 proposes max five sends with 1,2,4,8 second delays then Reservation query/background query every 30s; it is described as configurable demo policy, not implemented worker behavior (`docs/requirements/06-design-decisions.md:140-153`; detailed UC-02-B `docs/requirements/08-detailed-use-cases.md:216-223`). Confirm these values/config applicability before implementing; do not hardcode from plan.

## 4. Inventory client and verified outcomes

Proposed client should use the RESERVE snapshot saved at POST time, not reconstruct current catalog values; `OrderService` persists `saga_payload` and `request_payload` for step (`OrderService.java:101-103`; Saga schema V002:69-96; V003 preserves/normalizes snapshot lines 1-10). Send the exact stored request and `Idempotency-Key: reserve:{orderId}:v1` on every send.

Choose one route/shape after contract check:

- Main documented contract: `POST /api/v1/inventory/reservations` → 200 `Reservation` body with `status=RESERVED` or `REJECTED`, plus `rejectionReason`; response key/snapshot semantics documented at `docs/architecture/14-inventory-api-contract.md:11-56`.
- Internal source projection: `/internal/v1/reservations` → response has `status` and `reasonCode`, requires internal correlation header under contract extension (`.../14-inventory-api-contract.md:148-168`; controller `InventoryController.java:14-18,34-39`; projection `InventoryContractResponses.java:10-22`). Use only if this profile is selected and its compatibility/authentication contract is confirmed; docs explicitly caution not all implementation is compatible with PR #39.

For either selection, only a parsed, contract-valid persisted response with `status=REJECTED` is verified business rejection. Do not map HTTP 404 from inventory lookup, 5xx, network timeout, or connection reset to REJECTED. Inventory's own DB transaction locks the Order guard, replays by key/hash, and atomically saves effect/result (`InventoryService.java:32-68`); the Order client must preserve reservation ID/key/payload, not mint new values on retry. For lost response, query existing Reservation (prefer stable key/order selector) then replay same key/body if appropriate; query NOT_FOUND during a possible in-flight request does not prove no effect (`14-inventory-api-contract.md:62-67`).

## 5. Order/Reservation result mapping

| Inventory result | Reservation record expected | Saga RESERVE step expected | Order status expected | Existing guard / gap |
|---|---|---|---|---|
| Verified success | `RESERVED`, verified | `SUCCEEDED`, failure class `NONE` | `PENDING` (waiting for later payment workflow) | `recordReservation` accepts verified RESERVED; no worker/step result coordinator currently. Do not confirm without Capture. |
| Verified business rejection | `REJECTED`, verified | `FAILED`, failure class `BUSINESS` | `COMPENSATING` after `startCompensation(INVENTORY_REJECTED)` | Existing Order update requires `PENDING` + verified REJECTED (`OrderStateRepository.java:68-74`). Must coordinate Reservation, Saga step and Order/Saga status in one local transaction. |
| Transport timeout/response lost/outcome unknown | `UNKNOWN`, not verified, `unknownOperation=RESERVE` | `UNKNOWN`, failure class `UNKNOWN`, reconciliation metadata | `PENDING` unless expiry branch already owns the Order | Machine guards allow UNKNOWN; no worker/reconciliation implementation. Do not conclude failure. |
| Explicit retryable infrastructure error | If no proof of operation result, keep unknown/unresolved; if confirmed no effect, retain prior verified reservation value or NOT_CREATED only if evidence says so | Typically `IN_PROGRESS`, class `TRANSIENT`, next attempt scheduled per approved policy | Keep current nonterminal Order state; do not transition to FAILED | V004 requires TRANSIENT↔IN_PROGRESS; exact outcome mapping requires operation semantics. Inventory 503 retryable alone does not prove effect absent. |
| Key/payload conflict or invalid request | Do not overwrite a previously verified reservation; treat as integration/protocol fault and preserve diagnostics | Failure classification/reconciliation needs deliberate policy; never treat as normal stock rejection | Do not set `COMPENSATING` from unverified/inconsistent data | API returns explicit 4xx conflicts/validation; worker policy not implemented. |

Expiry race: existing expiry claim can move Order away from PENDING while RESERVE HTTP is in flight. On verified late REJECTED, worker cannot assume `startCompensation` succeeds; reload Order and follow the expiry branch's verified guard. On late `RESERVED`, use existing Inventory release/cancel contract only under an approved compensation path and stable release/cancel key; don't silently continue capture after Order left PENDING (UC-02-D, `docs/requirements/08-detailed-use-cases.md:219`). This edge needs a dedicated decision/test before broadening slice beyond rejection path.

**Test-first limitation:** A black-box test using only existing HTTP types can compile today, but the requested verified Inventory result has no caller/worker path to drive it. A test that manually invokes state-machine methods can prove existing transition logic, not asynchronous processing; a test-side worker would be implementation disguised as fixture. Therefore no new test can presently produce the required behavioral FAIL without one of those invalid shortcuts. After this plan is accepted, establish the worker/client seam and a live deterministic downstream fixture design first; keep each new test narrowly targeted and ensure the fixture confirms the actual HTTP call before assessing the expected state assertion.

## 8. Risks and mitigation

| Risk | Planned mitigation | Test evidence |
|---|---|---|
| Two workers claim one step | Atomic conditional claim/row lock; dispatch only returned owner; token fencing on every result write. Finder alone is insufficient. | T07 with concurrent worker instances and one downstream request/effect. |
| Worker dies after Inventory commits but before local result persists | Retry/reconcile using immutable reservation ID, same key and payload; Inventory returns original saved operation. No DB transaction held over HTTP. | T05 inject commit-then-drop-response; compare Inventory reservation/effect count and Order DB. |
| Retry creates duplicate reservation | Keep `reserve:{orderId}:v1`, reservation ID and request snapshot across attempts; conflict on different payload is a fault, never mint a new identity. Inventory lock/replay/hash supports this. | T05 assert one reservation/effect after retry and same key/payload on recorded requests. |
| Timeout although downstream succeeded | Treat as UNKNOWN/unresolved; query Inventory by order/key; only classify verified response as RESERVED/REJECTED; never convert transport timeout into FAILED. | T06/T05: commit-then-timeout and subsequent query/replay. |
| Order expires while Reserve is in flight | Re-read/conditionally transition current Order after response; late verified result follows expiry/compensation rules (UC-02-D), never launches payment after leaving PENDING; if late RESERVED, require confirmed release/cancel outcome. | Add a separate race test before expanding beyond the rejection slice; barrier worker vs expiry claim and verify no orphan reservation. |
| Compensation races/late result | Persist verified reserve outcome first atomically with step result; `startCompensation` only wins from PENDING; reject stale worker via token; handle branch that already left PENDING. | T03/T07 plus dedicated expiry race test; current source does not cover all worker/expiry timing. |
| HTTP inside DB transaction | Claim/record in short local transactions; downstream call between them. Configure connect/read timeout only after runtime requirement is agreed. | Integration test verifies result persisted after call; review transaction boundary and failure injection. |
| Outbox mistaken for dispatch | Outbox accepts only terminal events and has no publisher in Order runtime; don't use it for RESERVE without separately designing a request outbox/event contract. | Scope/static review; terminal Outbox regression tests remain separate. |
| p95 ≤ 2.0s / 60 concurrent users | POST should return after local Order+intent commit, independent of Inventory latency; GET reads persisted status. Benchmark submit/query under the defined 60-user workload after implementation; record latency and errors; do not claim target met without measurements. | Later performance run against agreed environment/workload; not run in this planning step. |
